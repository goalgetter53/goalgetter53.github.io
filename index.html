01

Account intelligence graph

Signals · Entity resolution · Scoring

Problem
Buying signals come in from many sources, and they all spell the same company differently. Naive joins either duplicate accounts or merge companies that are actually different.
Built
Async connectors pull SEC Form D funding filings, Greenhouse, Lever and Ashby job boards, GitHub and news. An entity-resolution engine (blocking → Jaro-Winkler/TF-IDF features → trained scorer → union-find) merges mentions into canonical accounts, which are then scored with time-decayed signals. It runs incrementally on DuckDB, with a FastAPI and CLI front end.
Result
F1 0.974 on a 173-record hand-labelled gold set, vs 0.784 for an exact name/domain join. ~4,000 records/s at 50k records. A live run pulled 809 real signals and exposed a fund-vehicle merge bug, which is now fixed.

02

Learning enrichment waterfall

Enrichment · Bandits · Reliability

Problem
Static cheapest-first waterfalls burn enrichment credits, because which provider works best depends on country, company size and seniority.
Built
A self-hostable enrichment orchestrator. A contextual Thompson-sampling router learns the best provider order for each segment. It runs on a crash-safe SQLite job queue with leases, plus token-bucket rate limits, circuit breakers, a budget-capped cost ledger and idempotency keys.
Result
Simulation (50k contacts × 5 seeds): cost per verified email down 20.9% vs a static waterfall, closing 80% of the gap to the oracle. A provider outage costs only 0.9 pp of coverage. Property tests caught a real rate-limiter hang.

03

Multi-agent outbound copilot on Claude

AI agents · Guardrails · Evals · A/B

Problem
AI-written outbound is generic, invents facts and is easy to hijack through prompt injection hidden in the web pages it reads.
Built
Researcher, strategist, copywriter and critic agents run on an explicit state machine. Every claim in the copy must cite a checked research fact. It adds prompt-injection defences, cost budgets, traced spans and regression evals across prompt versions, a Bayesian A/B module, and a human approval queue. Nothing is ever auto-sent.
Result
0/14 red-team injection pages got through (10/14 with the defences off). In mock-mode evals, prompt v2 took clean first drafts from 17% to 100% and cut estimated cost per sequence by 40%. A/B simulation showed peeking at results inflates false winners from 6% to 21%.

04

Bi-directional CRM sync engine

Reverse ETL · HubSpot · Data integrity

Problem
The CRM and the warehouse drift apart. Syncs overwrite reps' edits and create duplicates, and nobody can see what a sync will change before it runs.
Built
Two-way warehouse ↔ HubSpot sync driven by a declarative YAML mapping with per-field conflict rules. A three-way diff produces a Terraform-style plan before apply. It batches API calls under rate limits, splits and retries partial failures, and keeps a dead-letter queue with replay. Tests run against a fake HubSpot server.
Result
Benchmarked against a fake HubSpot API: a 50k-record load used 75× fewer API calls than one-by-one syncing, with 0 rate-limit errors under Starter limits. In a fault run (43 rate-limit errors, 28 server errors, 16 lost responses), exactly the 25 bad rows were dead-lettered and the other 49,975 had 0 mismatches. Hypothesis state-machine tests show the sync converges and re-runs are no-ops.

05

Attribution lab with ground truth

Analytics engineering · Attribution

Problem
Teams move budget based on attribution models nobody has ever validated. Last-touch quietly over-credits the final channel.
Built
A synthetic B2B world with known channel effects. A DuckDB SQL warehouse is built in layers (21 models, 59 data tests). It runs first/last/linear/time-decay/U/W, Markov removal-effect and Shapley attribution, then scores each model against the truth across seeds and confounding levels, alongside Kaplan-Meier funnel timing.
Result
On synthetic data, last-touch had the lowest average error but ranked channels almost at random (ρ 0.12–0.23). It gave organic 17–21% credit when organic's true effect is zero, and gave webinars ~10% when their true share is ~27%. I report this honestly rather than presenting a model win.

How I work

GTM engineering is revenue problems first and tools second.

1 · Diagnose

Start from the funnel. Where is pipeline leaking: targeting, data, copy, deliverability or speed-to-lead? Define the ICP before building anything.

2 · Build

Use Clay and n8n where they're fastest, and Python, APIs and Claude agents where they hit limits. Version-control everything and document it for handover.

3 · Measure

Track coverage, cost per enriched contact, reply and meeting rates. Run weekly experiments and cut what doesn't move pipeline.
